# Структура DWH

## Поток данных
```text
CSV → raw → staging → data_mart → data_mart_report → Metabase
```

## 1. `raw` — исходные данные

Назначение: сохранить данные из источника в табличном виде максимально близко к источнику.

Правила:
- имя таблицы совпадает с именем CSV-файла;
- сохраняются исходные колонки и техническое время загрузки `loaded_at`;
- `id` исходной записи не обязан быть уникальным, поскольку `raw` хранит все обнаруженные версии;
- преобразования бизнес-данных не выполняются;
- каждая модель `staging` запускается после успешной загрузки соответствующей таблицы `raw`;
- независимые ветки выполняются параллельно, а последующие модели ожидают только собственные входные данные.

При первом запуске таблицы загружаются полностью. Далее Airflow сравнивает входящую строку с последней загруженной версией того же бизнес-ключа. Новая или изменившаяся версия добавляется через `INSERT`, неизменившаяся не записывается. Предыдущие версии никогда не обновляются и не удаляются.

## 2. `staging` — очистка и типизация

Назначение: выбрать последнюю версию каждой исходной записи и подготовить данные к загрузке в размерную модель.

Правила:

- преобразовать значения в требуемые типы PostgreSQL;
- выбрать последнюю версию бизнес-ключа по `loaded_at`;
- нормализовать строковые значения;
- проверить обязательные поля и уникальность идентификаторов;
- завершать загрузку ошибкой при критическом нарушении качества.

Для каждой исходной таблицы создана соответствующая staging-модель. Названия некоторых колонок и их типы нормализуются.

Отдельную таблицу для отклонённых строк в рамках учебного проекта не создаём.

## 3. `data_mart` — размерная модель Kimball

Назначение: хранить согласованные измерения и факты на атомарном уровне.

Grain каждой таблицы фактов: одна строка — одна операция из источника.

Используем отдельную таблицу фактов для каждого бизнес-процесса. Общие измерения связывают процессы между собой.

## 4. `data_mart_report` — отчётные витрины

Назначение: предоставить Metabase простые готовые наборы данных под конкретные бизнес-запросы.

Metabase подключается к объектам слоя `data_mart_report`, а не к техническим слоям `raw` и `staging`.

## Инкрементальная обработка

Для `deposits`, `withdrawals`, `games` и `currency_rates` используется sliding lookback window размером 30 дней. Нижняя граница рассчитывается как максимальная бизнес-дата, уже загруженная в raw, минус 30 дней.

Для `players`, `providers_map` и `games_map` нет поля с датой изменения. Эти небольшие таблицы читаются целиком, но в `raw` добавляются только новые и изменившиеся версии.

CSV-файлы физически просматриваются целиком, поскольку у них нет индексов. Отбор по окну уменьшает объём записи в PostgreSQL и дальнейшей обработки dbt, но не объём чтения самого файла. Для учебного проекта это имитирует polling источника с ограниченным набором доступных полей.

Модели `staging`, измерения и факты используют incremental-материализацию dbt. `player_metrics` и `metrics_overview` заменяют только строки за даты, затронутые изменениями. `monthly_summary` остаётся представлением.

### Допущения и ограничения

- идентификаторы и бизнес-даты операций неизменяемы;
- источник не предоставляет `created_at`, `updated_at` и `deleted_at`;
- по бизнес-правилам сущности не изменяются позднее 30 дней после создания, где это допущение применимо;
- опоздавшие записи и исправления появляются внутри 30-дневного lookback-окна;
- источник не выполняет физические удаления значимых записей;
- изменения старше окна не обнаруживаются, потому что источник не предоставляет `updated_at` или CDC;
- размер окна является настраиваемой бизнес-договорённостью, а не гарантией источника.
